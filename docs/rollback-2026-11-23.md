## Порядок отката

Идём от дешёвого к дорогому и останавливаемся, как только прежнее поведение вернулось.

1. **Вид.** Если не понравилась только оболочка, ничего откатывать не нужно: без `?skin=living` её нет.
2. **Выкладка.** Если новая карта на бою ведёт себя плохо, возвращаем прежнюю выкладку кнопкой Instant Rollback в Vercel. Прежний код работает с базой после миграций: новые поля `places` он не читает, новая функция ему не нужна.
3. **Код.** Если решено убрать новую карту из `main`, делаем revert коммита слияния отдельным PR. Историю не переписываем, force-push запрещён.
4. **База.** Только если мешают сами изменения базы. Обычно этот шаг не нужен.

Проверено запросом к боевой базе 25.11 после применения: индекса `places_one_public_submission_per_creator_idx` нет; триггер `places_lock_moderation_status` стоит, функция замка в редакции с пропуском сеансов без JWT; `submit_mapper_place` есть, `SECURITY DEFINER`, выполнять может `authenticated` и `service_role`, у `anon` и `public` права нет; правило `place_photos_storage_read_own` есть; `add_karma` закрыта для `anon` и `authenticated`; в `places` по-прежнему одна строка.

**Как применялись последние четыре.** Коннектор Supabase на удаление индекса просит подтверждение окном, которое в треде проекта не нажимается, поэтому миграции ушли через Supabase CLI 3.4 командой `scripts/db-push.sh` (см. ниже). Пароль базы не нужен: CLI подключается через вход в Supabase.

**Снимок до изменений.** Схема `rollback_20261123` внутри той же базы: копии `places` (1 строка), `photos` (1), `profiles` (3), `karma_events` (2) и таблица `definitions` (45 строк) с прежними текстами функций, определениями индексов `places`, правилами доступа и списком миграций. Схема не входит в список схем API, прав у ролей `anon` и `authenticated` на неё нет (проверено `has_schema_privilege`).

**Откат функции и правила пути картографа.** `supabase/rollback/2026-11-23_new_map_down.sql`, шаг 1: убирает функцию подачи и правило «автор читает свои фото». Карточки, уже поданные на проверку, остаются строками `places` со статусом `pending`; публике они не видны.

**Откат полей.** Тот же файл, шаг 2, закомментирован: удаление полей стирает записанные в них данные и для возврата к прежнему приложению не требуется.

**Роль модератора.** Тот же файл, шаг 3, закомментирован: возвращает профилю роль из снимка. Побочное действие роли: `submit_public_place` принимает только `public_user`, поэтому с ролью `admin` публичная подача серой метки этому профилю недоступна; путь картографа роль `admin` принимает.

**Замок и лимит.** Тот же файл, шаг 4, закомментирован. Замок убирать только вместе с шагом 1.

**Журнал миграций.** Записи в `supabase_migrations.schema_migrations` идут под номерами файлов из `supabase/migrations/`; две миграции, применённые коннектором 23.11, выровнены под номера файлов вручную. Повторный пробный прогон `supabase db push --dry-run` 25.11 ответил «Remote database is up to date».

**Миграции одной командой.** `npm run db:push` (скрипт `scripts/db-push.sh`): пробный прогон, список к применению, вопрос «Применить?», применение, сверка. Нужны Supabase CLI 3.x и вход `supabase login`. Применение к боевой базе по-прежнему только по слову Алхаса.

Проверено на локальном PostgreSQL 16 (все 13 миграций, затем файл отката с шагами 1 и 2): набор полей `places`, отсутствие функции и правила совпадают с базой до миграций `20261001100000…20261123120000`; `submit_public_place` на месте.

Не проверено: шаг 4 файла отката; сквозной проход пути картографа на боевой базе (вход, фото, подача, публикация); работает ли на сервере регулярная копия `scripts/supabase_backup.sh` (каталог `/srv/ais/backups/goapsny`). Снимок в схеме `rollback_20261123` от неё не зависит.
