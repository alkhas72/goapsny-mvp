## Модульность: как устроено

База делится на ядро и модули.

- **Ядро** (`public`): `places` (общий список заведений для карты и всех модулей), `profiles` (люди и роли), вход.
- **Модуль** — своя схема Postgres. Первый модуль — `ramps`: заявки, изделия, осмотры, история, фото.

Правила модуля:

1. Модуль ссылается на ядро только по `place_id` и `profile_id`. Ядро о модуле не знает: в `public` нет ссылок на таблицы `ramps`.
2. Наружу, на карту, модуль отдаёт одно значение: `places.ramp_type`. Его ставит триггер модуля при установке и снятии пандуса. Это единственная запись модуля в ядро.
3. Сотрудник модуля видит данные модуля и короткую карточку заведения (`ramps.place_card`: название, адрес, координаты, контакт), без остальных полей карты.
4. Модуль выгружается целиком без остального: `pg_dump --schema=ramps` плюс `ramps.place_card`. Удаление модуля не трогает ядро.
5. Свой бакет: `ramp-photos`.

Прецедент отдельной схемы уже есть: `goapsny_private` (миграция `20260715120000`).

Сейчас наружу через Data API открыта только `public` (в `supabase/config.toml` нет раздела `[api]`, значит действуют значения по умолчанию). Для модуля схему `ramps` нужно добавить в открытые схемы: локально в `config.toml`, в бою — в настройках проекта Supabase. Это делает Алхас или с его согласия.

Туалеты и парковки сейчас — поля в `places` (`toilet_exists`, `toilet_accessible`, `parking`, миграция 0001). В этой работе их не трогаем. Когда для них понадобятся подробности (замеры кабины, число мест, обслуживание), они станут модулями `toilets` и `parking` по тем же правилам, а поле в `places` останется сводкой для карты.

## Что уже есть в ядре и что берём

- `places` — единый список заведений (контрагентов). Новый список не заводим.
- `places.ramp_type` уже знает `portable_on_request` и `portable_available`.
- Новое заведение от участника без роли сборщика создаётся через существующий `submit_public_place`.
- `profiles` — роли и `telegram_id`; чужой профиль читают только сам владелец и admin/owner (`profiles_read_own_or_admin`).
- Вход через `auth-telegram`.
- `karma_events` — основа для благодарности.

## Вход

Предлагаю открывать Stopgap как Mini App того же бота. Тогда работает уже существующий путь `auth-telegram` (Telegram `initData` → JWT), и это телефон, где проходит 90–95% замеров.

Вход из обычного браузера через Telegram Login Widget требует другой проверки подписи. Это отдельная работа, позже.

Версия в claude.ai остаётся демонстрационной.

## Схема модуля `ramps` (эскиз, не SQL миграции)

### Ядро: `profiles` — новые колонки

| Колонка | Что хранит |
|---|---|
| `full_name text` | Имя и фамилия, вводятся один раз |
| `phone text` | Телефон |

Имя и телефон нужны не только пандусам, поэтому они в ядре. Видимость не меняется: свой профиль видит владелец, все профили видят admin и owner. Анонимные заявки не принимаются: без `full_name` и `phone` отправка заявки отклоняется (проверяет RPC).

### `ramps.place_card` — представление

Короткая карточка заведения для сотрудников модуля: `id`, `name`, адрес, `lat`, `lng`, контакт. Только заведения, у которых есть место установки в модуле.

### `ramps.sites` — место установки

У одного заведения может быть несколько мест: вход, подиум, туалет.

| Колонка | Что хранит |
|---|---|
| `id uuid` | |
| `place_id uuid` | Ссылка на `public.places` |
| `label text` | Например «главный вход», «подиум у сцены» |
| `created_by` | |
| `created_at` | |

### `ramps.requests` — заявка (замер)

| Колонка | Что хранит |
|---|---|
| `id uuid` | |
| `site_id uuid` | Место установки |
| `author_id uuid` | Ссылка на `public.profiles` |
| `status text` | Значения — в разделе «Статусы и переходы» |
| `measure jsonb` | `{hl, hr, freeWidth, width, raw:{...}}`, числа как на рулетке |
| `result jsonb` | Расчёт `build()` из Stopgap `src/ramp.js` и `paramsVersion` |
| `paint jsonb` | `{hex, ral, name}` |
| `notes jsonb` | Голосовые и письменные заметки `[{step, text}]` |
| `extra_note text` | |
| `comment text` | |
| `progress smallint` | 0–100: пять снимков по 20% (А, Б, ширина, общий план, примерка) |
| `submitted_at`, `created_at`, `updated_at` | |

### `ramps.request_photos` — снимки заявки

| Колонка | Что хранит |
|---|---|
| `id` | |
| `request_id` | |
| `step` | Один из `hl`, `hr`, `free`, `overview`, `extra`, `fit` |
| `storage_path` | Путь в бакете |
| `w`, `h` | Размеры снимка |
| `created_at` | |

Бакет `ramp-photos` закрытый, путь `{request_id}/{step}-{n}.jpg`.

### `ramps.units` — изделие

Одно изделие на одну заявку.

| Колонка | Что хранит |
|---|---|
| `id` | |
| `request_id` | |
| `made jsonb` | Размеры по факту раскроя и сборки |
| `paint_ral` | |
| `made_by`, `made_at` | |
| `installed_by`, `installed_at` | |
| `onsite jsonb` | Зазор и перепад у ступени слева и справа, с фото |
| `removed_at` | |

### `ramps.events` — история заявки

| Колонка | Что хранит |
|---|---|
| `id` | |
| `request_id` | |
| `from_status`, `to_status` | |
| `actor_id` | |
| `reason text` | Например, что не так в замере |
| `at` | Время события |

Пишется только из RPC.

### `ramps.service` — обслуживание

Плановые осмотры, ремонт, покраска, замена.

| Колонка | Что хранит |
|---|---|
| `id` | |
| `unit_id` | |
| `kind text` | `inspection`, `repair`, `repaint`, `replace` |
| `due_at` | Срок |
| `done_at`, `done_by` | |
| `condition jsonb` | Краска, крепёж, устойчивость, износ |
| `photos` | |
| `next_due_at` | Следующий срок осмотра |

Первый осмотр — через 6 месяцев после установки, дальше раз в год. Срок предварительный, ждёт подтверждения Алхаса.

### `ramps.auditor_options` — расширенный аудит по желанию

Алхас, 2026-11-08: расширенный аудит (потоковое видео) — предложение в личном кабинете, а не обязанность. Открывается после N замеров и только если человек сам захочет.

| Колонка | Что хранит |
|---|---|
| `profile_id` | |
| `option text` | Пока одно значение: `live_video` |
| `offered_at` | Когда порог пройден и предложение показано |
| `accepted_at` | Когда человек сам включил; пусто, если не включал |
| `declined_at` | Когда отказался; предложение больше не показываем |

Порог N задаёт Алхас: назывались 10, 20 и 25 замеров.

### Представление `ramps.auditor_stats`

Число заявок, установленных пандусов и перезамеров на аудитора. Отсюда считается, пройден ли порог для `auditor_options`.

## Роли

- Аудитор (`public_user` и выше): создаёт свои заявки, видит свои заявки и их статусы.
- Сотрудник обслуживания пандусов: новая роль модуля, например `ramp_service`. Видит весь модуль `ramps` и `ramps.place_card`, больше ничего из базы. Отмечает изготовление, установку, осмотры, ремонт.
- admin, owner: всё.

Роль модуля хранится в модуле (`ramps.staff(profile_id, role)`), а не в `profiles.role`: так другой модуль заводит своих сотрудников, не меняя ядро.

## Статусы и переходы

| Из | В | Кто | Как |
|---|---|---|---|
| — | `draft` | автор | insert |
| `draft`, `remeasure` | `submitted` | автор | RPC `ramps.submit(request)`: проверяет 4 обязательных фото, числа, `full_name` и `phone` профиля |
| `submitted` | `accepted` / `remeasure` | `ramp_service`, admin, owner | RPC `ramps.set_status(request, to, reason)`; для `remeasure` `reason` обязателен |
| `accepted` | `production` → `ready` | то же | то же |
| `ready` | `installed` | то же | то же + `ramps.units.installed_*`; триггер ставит `places.ramp_type` (значение — вопрос 2) |
| `installed` | `service` | по дате | задача по расписанию по `ramps.service.due_at` |
| любой после `installed` | `removed` | `ramp_service`, admin, owner | триггер снимает `places.ramp_type` |

Каждый переход пишет строку в `ramps.events`.

## Правила доступа (дополнение к `docs/rls-checklist.md`)

- Автор читает свои заявки, их фото, события и изделия. `ramp_service`, admin и owner читают весь модуль.
- `ramp_service` не читает таблицы ядра напрямую, только `ramps.place_card` и имя и телефон автора своих заявок через RPC.
- Автор меняет заявку только в `draft` и `remeasure`. Статус меняется только через RPC.
- `banned` ничего не создаёт.
- `public_user` может создать заявку (Алхас: «любой человек может зарегистрироваться»). Новое заведение он заводит через `submit_public_place`.
- Публично, без входа, наружу уходит только `places.ramp_type`.
- Фото заявки на карту не попадают.
- `ramps.events` и `ramps.service` пишутся только из RPC и задач (security definer, `search_path` закреплён).
- Проверить по образцу 0001: RLS включена на всех таблицах модуля, `anon` не имеет прав на схему `ramps`.

## Что меняется в Stopgap

- Шаг «Кто и где» сжимается до «Где»: заведение из списка рядом или новое.
- Профиль заполняется один раз.
- Появляются «Мои заявки» со статусами, полосой готовности и причиной перезамера.
- После порога в кабинете появляется предложение расширенного аудита; включается только по желанию.
- Отправка заявки идёт в модуль `ramps` и бакет вместо хранилища claude.ai.
